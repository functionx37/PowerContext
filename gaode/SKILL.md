# 周边去哪儿

完成一次“理解需求 → 搜索高德地点 → 查询步行路线 → 筛选并回答”。所有推荐都是从用户给定的**同一起点**出发的独立备选，不串成多站行程。地点事实来自本次高德查询，步行距离与时间来自对应的步行路线，不能凭记忆补齐。

## 1. 理解需求并固定起点

- 提取城市、起点名称与坐标、地点类型、时间或距离上限、推荐数量、排序偏好和排除条件。
- 使用用户或平台提供的起点坐标，按工具要求传入，通常为 `经度,纬度`；不得颠倒、改成城市中心或某个候选地点，不另做设备或 IP 定位。起点名称仅用于表达。只有坐标缺失、无效或与城市明显冲突且无法消解时，才简短请求补充或确认，不猜坐标。
- 推荐数量默认 3；用户指定更少则遵从，指定更多也最多 3 个，并简短说明本次最多推荐 3 个。用户明确不需要推荐时不强行搜索。
- 将“步行不超过 15 分钟”转为硬条件 `duration_seconds <= 900`；“少于 15 分钟”用严格小于。未指定时间上限时，不擅自增加时间门槛。明确的地点类型、距离上限、排除条件同样必须满足。
- 区分硬条件与偏好：“必须营业”“只要免费”需要数据证实；“优先安静”“最好不排队”属于偏好。无法核实的偏好不当作已满足，无法核实的硬条件不当作合格。不要把全部自然语言塞进搜索关键词。

## 2. 选择平台提供的高德工具

使用当前环境已配置的高德 MCP，先看实际工具说明和参数 schema。下面是常见名称与参数；名称可能带服务前缀，以平台暴露的对应能力为准，不调用不存在的工具，也不传 schema 不支持的参数。

| 能力 | 常见工具名 | 用途与关键参数 |
| --- | --- | --- |
| 周边搜索 | `maps_around_search` | `keywords` 为地点类别或品牌，`location` 为固定起点，`radius` 为搜索半径（米） |
| 步行路线 | `maps_direction_walking` | `origin` 为固定起点，`destination` 为该候选 POI 的坐标 |
| 详情查询（可选） | `maps_search_detail` | 用搜索结果的 `id` 补查坐标、地址或所需属性 |
| 关键词搜索（可选） | `maps_text_search` | 周边搜索不可用或需补充召回时，按 `keywords`、`city` 查找候选 |

核心链路只依赖地点搜索和步行路线；可选工具缺失时继续处理已有的可用数据。无需安装服务、申请或索取密钥，也不将密钥写入文件或回答。无需输出 JSON、导出调用日志或创建地图。

## 3. 搜索并整理候选地点

1. 选用直接的类别关键词，例如“咖啡馆”“餐厅”“公园”；指定品牌时保留品牌，不凭名称猜测它具备安静、低价等属性。用户允许多个类别时分别搜索，再合并去重。
2. 以固定起点做周边搜索。用户明确给出搜索半径时遵从；否则，有时间上限 `T` 分钟时可先用 `max(500, 100 × T)` 米，无上限时可先用 2000 米，并遵守工具允许范围。此半径仅用于召回，不代表步行可达范围，也不能据此断定满足时间条件。
3. 检查调用是否成功，再读取地点列表。若工具把 JSON 放在文本或内容块中，先解析真实数据；错误消息、空数组及空值不是有效地点。保存候选的 `id`、原始名称、地址、坐标、类型和确有返回的属性。
4. 依据类型、名称和地址剔除明显不相关地点及用户排除项；按 POI ID 去重，无 ID 时按名称、地址和坐标共同判断。同品牌不同门店可保留，同一地点的重复条目不重复推荐。关键词搜索得到的同名异城结果不得混入。
5. 坐标缺失时，如详情工具可用，按真实 POI ID 补查；仍无坐标则排除，不捏造终点。地址缺失时也可补查；仍缺失则在地址栏标注“高德未返回详细地址”，不能拿起点地址或其他门店地址填充。
6. 先选约 6 个类别匹配、位置接近的候选核验路线，结果不足时再补充。可使用更常见的同义词、工具支持的下一页，或在用户未限制搜索半径时适度扩大范围；不改变用户的时间上限、地点类型或排除条件。最多补搜两轮、核验约 12 个去重候选后收束，避免无限调用。只有实际核验过的候选才能进入推荐；不能把搜索顺序当作步行排名。

## 4. 逐一查询步行路线并筛选

对每个待核验候选调用步行路线：`origin = 固定起点坐标`，`destination = 当前 POI 的 location`。不同候选之间不相互作为起点，缓存本次相同起终点的成功结果，避免重复查询。

- 检查成功状态及有效的步行方案，通常位于 `route.paths` 或 `paths`；以实际返回结构为准。路线为空、工具报错、缺少总距离或总耗时，该候选均不能作为已核验推荐。
- 提取**同一个完整步行方案**的总距离和总耗时，通常为 `distance`（米）与 `duration`（秒）；工具明确采用其他单位时按其说明转换。数字字符串先转数值，空字符串、`null`、空数组和非法值不得当作 0。不得把路段的距离或时间当作全程，也不得拼接不同方案的最小值。
- 多个有效方案时，先剔除违反用户路线硬条件的方案；用户优先近时选步行距离最短的合格方案，同距离选耗时较短者，否则选耗时最短的合格方案，同耗时选距离较短者。没有合格方案则排除该地点。时间限制按原始秒数比较，距离限制按原始米数比较，**先筛选再换算展示**。
- 不用周边搜索的 `distance`、直线测距、驾车或骑行结果代替步行路线，不按固定步速估算耗时。河流、围墙和出入口造成的绕行以真实路线为准。
- 保留“POI → 终点坐标 → 所选路线 → 距离/耗时 → 合格与否”的内部对应关系，确保输出名称、地址、路线属于同一地点。

## 5. 排序并生成推荐理由

先应用所有硬条件，再排序，最后截取所需数量：

- “优先近一点”“距离最近”：按真实步行**距离升序**，相同距离按耗时升序。
- “最快到达”“步行时间最短”：按真实步行**耗时升序**，相同耗时按距离升序。
- 无明确排序偏好：优先类型匹配且满足有证据的偏好，再按步行耗时、距离升序。用户明确排序时，不让无依据的主观评价覆盖排序。
- 对这一批待核验候选完成路线筛选后再排序，不因先查到足够数量就直接输出。只能说“在已核验候选中较近/最近”，不能声称穷尽附近所有地点。
- 每个理由只写一句，引用可核对的事实，例如“咖啡馆类型匹配，在已核验候选中步行距离最短”。安静程度、排队、价格、评分、营业状态等，只有工具明确返回相关证据时才可引用；静态营业时间不等于实时营业确认。涉及用户偏好但无证据的属性写“未核实”，不凭品牌、商圈或公园类别推断。

## 6. 简洁回答

使用用户语言，默认简体中文。先用一句话说明起点和筛选条件，再列最多 3 个推荐。可用下列表格，或包含同样字段的列表：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 查询返回的真实名称 | 该 POI 的地址或明确的缺失说明 | 所选路线的距离（米） | 所选路线的预计耗时 | 一句有数据依据的理由 |

上表仅定义字段，实际回答必须替换为本次真实结果；没有合格结果时不输出占位行。保留高德返回的门店名和地址，可在有返回依据时补上市、区，不能自行编造街道或门牌。

- 距离可直接展示原始米数；时间将秒数换成“X 分 Y 秒”，整分钟可写“X 分钟”。若仅显示整数分钟则向上取整，不能向下取整掩盖超时。例如 901 秒不满足“不超过 15 分钟”；900 秒满足该条件，但不满足“少于 15 分钟”。
- 结尾简短注明“步行距离与预计耗时来自高德步行路线规划”；用户关心但未核实的属性，集中补一句或在对应理由中注明。不要堆叠与需求无关的免责声明或内部处理细节。
- 发送前检查：数量未超限；每行均有真实地点和对应的成功步行路线；均满足原始硬条件；顺序与声明的排序依据一致；理由有证据，缺失信息已说明。

## 7. 结果不足与异常

- **不足指定数量：** 完成有限补搜后，只返回已核验且合格的地点，说明“本次查询范围内仅找到 X 个符合条件的地点”。不能用超时、类型不符或路线缺失的地点凑数。
- **零个合格地点：** 不生成推荐表或虚构备选。区分“搜索未返回匹配地点”“已查询路线均超时/不符条件”“关键条件无法核实”，按实际原因简短说明。可建议用户放宽步行上限、半径或类型，但不擅自按放宽后的条件推荐，也不宣称全城没有。
- **临时超时或服务异常：** 对失败请求用相同参数最多重试一次；参数错误则按 schema 修正一次，鉴权或额度问题不反复重试。服务故障不能说成“附近没有地点”。
- **部分路线失败：** 继续核验其他候选，返回成功且合格的结果，并简短说明部分路线未能核验；失败候选不进入推荐。
- **搜索或路线能力持续不可用：** 如实说明本次无法完成真实地点/步行核验，建议稍后重试；不改用记忆、网页印象或直线距离生成结果，不把可疑数据当作服务成功。
- **硬条件证据不足：** 如“必须安静”但无可验证信息，说明无法确认该条件，不能宣称已找到符合要求的地点。软偏好证据不足则可继续推荐基础条件合格者，并标注相关属性“未核实”。
